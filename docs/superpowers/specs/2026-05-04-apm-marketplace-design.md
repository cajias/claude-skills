# APM Marketplace + OpenProse Programs — Design

**Date**: 2026-05-04
**Status**: Approved design, ready for implementation planning
**Repo**: `github.com/cajias/claude-skills`

## Goal

Convert this repository into an [APM](https://github.com/microsoft/apm)
marketplace that publishes:

1. The existing polished Claude Code plugins (currently distributed via
   Homebrew + hand-authored `.claude-plugin/marketplace.json`).
2. New OpenProse programs that orchestrate this repo's coding-quality
   skills as multi-service workflows.

APM replaces Homebrew as the distribution channel. Versioning continues
to be semver.

## Non-goals

- Touching the top-level `skills/` and `agents/` catalogs. They remain
  as-is.
- Migrating the 9 currently-hidden / WIP plugins. Only the 4 polished
  plugins are exposed.
- Building a runtime for OpenProse. The upstream `openprose/prose` skill
  is the VM; we ship programs and depend on it.

## Constraints (authoritative)

- `apm pack` writes `.claude-plugin/marketplace.json` byte-for-byte from
  `apm.yml`. The current hand-authored file becomes the compiled
  artefact and must round-trip cleanly.
- Local plugins use `source: ./plugins/<name>` with
  `metadata.pluginRoot: ./plugins`. APM emits paths relative to
  `pluginRoot` in the output.
- Each plugin needs a `plugin.json` (in `.claude-plugin/plugin.json`,
  `.github/plugin/plugin.json`, root, or `.cursor-plugin/plugin.json`).
  APM auto-maps `agents/`, `skills/`, `commands/` into the consumer's
  `.apm/` tree.
- OpenProse programs are _not_ skills. They are markdown payloads
  (`kind: program` or `kind: service`) that the upstream `open-prose`
  skill (the VM) interprets in-session. Distribution shape: a
  `commands/<name>.md` slash command points at a bundled
  `programs/<name>/index.md`.
- Each prose-program plugin declares `openprose/prose` as a dependency
  so APM resolves the VM into `.apm/skills/open-prose/` on install.
- Multi-service programs (multiple roles) require Claude's subagent
  primitive at runtime; this is a runtime fact, not a packaging
  concern.

Two phases, separately shippable.

The compiled `.claude-plugin/marketplace.json` must round-trip from

hand-authored file. `apm pack` produces it; we verify with a one-time
diff and commit.

#### Tooling additions

`Makefile` (new):

```make
.PHONY: pack check outdated help

pack:
 apm pack

check:
 apm marketplace check

outdated:
 apm marketplace outdated

help:
 @grep -E '^[a-zA-Z_-]+:.*?##' $(MAKEFILE_LIST) \
   | awk -F':.*?## ' '{printf "  \033[36m%-15s\033[0m %s\n", $$1, $$2}'
```

CI: a single GitHub Actions job runs `apm marketplace check` on every
PR. Blocks merge on schema or reachability errors. `apm marketplace

### Phase 2 — OpenProse programs with composable services

Three new prose-program plugins are added: `pr-review`, `tdd-cycle`,
`feature-execution`. Each is shipped as a separate APM plugin. Each
declares `openprose/prose` as a dep so `apm install` brings the VM
along.

#### Composability principle

Programs are built from small reusable **services**. A service is the
unit of composition: it owns one role with one `Requires`/`Ensures`
contract. Programs orchestrate services.

Concretely, in this marketplace:

- An **atomic service** is a single `.md` file with `kind: service`
  frontmatter, `### Requires`, `### Ensures`, and a body that defines
  one role.
- A **composite program** has `kind: program`, lists its services in
  `### Services`, and references them by **relative path** within its
  own `programs/<name>/` directory.
- Services SHOULD be designed for reuse — names, contracts, and prompt
  content should not assume a single calling program. A `code-review`
  service should be drop-in usable wherever a code review is needed.
- **Service ownership in v0.1 is per-plugin and reuse is per-plugin.**
  Each plugin's `programs/<name>/` co-locates its own services.
  Cross-plugin service reuse is a planned future evolution but out of
  v0.1 scope (see "Cross-plugin reuse" below for why).
- Where two plugins legitimately need the same service shape (e.g.
  both `pr-review` and `tdd-cycle/refactor` want `code-review`), the
  v0.1 answer is to copy the service file. The contract is documented;
  copies stay in sync by convention until the cross-plugin mechanism
  lands.

#### Cross-plugin reuse (deferred)

OpenProse's `use "host/owner/repo"` directive imports remote programs
by cloning them into a runtime `.deps/` cache — a mechanism that is
**independent of APM**. APM-installing a plugin does not pre-populate
`.deps/` for OpenProse; conversely, OpenProse's `.deps/` does not
satisfy APM's transitive resolution. Cross-plugin service reuse
therefore requires a deliberate design choice (e.g. a shared
`prose-services` library plugin, or a `use`-by-relative-path convention
validated against OpenProse semantics) that we do not have evidence to
settle in v0.1.

The v0.1 cost of duplication across three programs is small and the
savings of a premature cross-plugin mechanism are speculative. We
revisit this once we have ≥2 services with stable contracts that the
second program demonstrably wants verbatim.

#### Plugin shape (Phase 2 — generic)

```text
plugins/<program-name>/
├── .claude-plugin/plugin.json
├── apm.yml                              # deps: openprose/prose
├── README.md
├── commands/<program-name>.md           # slash command activates VM
└── programs/<program-name>/
    ├── index.md                         # kind: program; Services; orchestration
    ├── <service-a>.md                   # kind: service; owned by this program
    ├── <service-b>.md                   # kind: service; owned by this program
    └── ...
```

Per-plugin `apm.yml`:

```yaml
name: <program-name>
version: 0.1.0
description: <one-line>
dependencies:
  apm:
    - openprose/prose
```

Per-plugin `commands/<program-name>.md`:

```markdown
---
description: Run the <program-name> OpenProse program
---

Activate the `open-prose` skill and run the program at:
`${CLAUDE_PLUGIN_ROOT}/programs/<program-name>/index.md`

Multi-service programs run roles via Claude's subagent primitive per
OpenProse semantics. Do not shell out to a `prose` binary.
```

#### Program 1 — `pr-review`

Multi-service code review. Reproduces what the user assembles manually
today by invoking each `pr-review-toolkit` specialist.

```text
plugins/pr-review/
├── .claude-plugin/plugin.json
├── apm.yml                              # deps: openprose/prose
├── commands/pr-review.md                # /pr-review <PR-ref>
└── programs/pr-review/
    ├── index.md                         # kind: program
    │                                    # Services: [coordinator,
    │                                    #            code-review,
    │                                    #            security-review,
    │                                    #            test-analysis,
    │                                    #            type-review,
    │                                    #            comment-review]
    ├── coordinator.md                   # gathers diff, dispatches, aggregates
    ├── code-review.md                   # correctness + style
    ├── security-review.md               # OWASP / secrets / injection patterns
    ├── test-analysis.md                 # coverage of new code, missing edges
    ├── type-review.md                   # type design + invariants
    └── comment-review.md                # comment-vs-code drift
```

**Contracts** (canonical sketch — exact wording belongs in
implementation):

- `coordinator.Requires`: a PR identifier (URL, branch ref, or local
  diff range).
- `coordinator.Ensures`: a review report aggregating results from all
  five specialists, ordered by severity.
- Each specialist `Requires`: a unified diff + repo context.
- Each specialist `Ensures`: a list of findings, each with
  `{severity, location, summary, suggestion}`.

**Source skills** (Phase 2 lift):
`plugins/pr-review-toolkit/skills/*/SKILL.md` if present, otherwise
the existing `code-reviewer` / `silent-failure-hunter` /
`pr-test-analyzer` / `type-design-analyzer` / `comment-analyzer` agent
definitions. Each becomes a service in `programs/pr-review/`.

**Reuse**: `code-review.md` and `test-analysis.md` are designed
contract-first so that future programs (e.g. `tdd-cycle/refactor`,
`feature-execution/post-impl`) can drop in copies. v0.1 keeps copies
separate per the deferred cross-plugin decision.

#### Program 2 — `tdd-cycle`

Multi-service phased program: plan → red → green → refactor.

```text
plugins/tdd-cycle/
├── .claude-plugin/plugin.json
├── apm.yml                              # deps: openprose/prose
├── commands/tdd-cycle.md                # /tdd-cycle <feature-description>
└── programs/tdd-cycle/
    ├── index.md                         # kind: program; phases:
    │                                    #   plan → red → green → refactor
    ├── planner.md                       # generates the iteration plan
    ├── red.md                           # writes failing test, asserts fail
    ├── green.md                         # minimal impl, asserts test passes
    ├── refactor.md                      # cleanup with regression check;
    │                                    # gates on local code-review
    └── code-review.md                   # local copy of code-review service
```

**Contracts**:

- `planner.Requires`: feature description.
- `planner.Ensures`: ordered list of test cases each with
  `{name, intent, expected-failure-mode}`.
- `red.Requires`: a single test case from planner.
- `red.Ensures`: a committed failing test + observed failure output
  matching the expected mode.
- `green.Requires`: the failing test.
- `green.Ensures`: the test passes; no other tests regressed.
- `refactor.Requires`: passing test suite.
- `refactor.Ensures`: same passing suite + a `code-review` clean bill,
  no behavior change.

**Composition**: `refactor.md` references `code-review.md` co-located
in `programs/tdd-cycle/`. The contract matches
`pr-review/programs/pr-review/code-review.md` so the two stay
swap-compatible when the cross-plugin mechanism lands.

**Resilience**: Context-compaction resilience (from
`skills/tdd-context-compaction-resilience/`) is encoded as
`### Invariants` in `index.md` — phase identity (RED/GREEN/REFACTOR)
is recoverable from the workspace state, not session memory.

**Source skills**: `skills/tdd-plan/`,
`skills/tdd-context-compaction-resilience/`.

#### Program 3 — `feature-execution`

Multi-phase orchestrator that runs an architecture plan, calling
`tdd-cycle` per phase.

```text
plugins/feature-execution/
├── .claude-plugin/plugin.json
├── apm.yml                              # deps: openprose/prose
├── commands/feature-execution.md        # /feature-execution <plan-or-spec>
└── programs/feature-execution/
    ├── index.md                         # kind: program; iterates phases
    ├── architect.md                     # validates phase pre-implementation
    ├── implementer.md                   # phase implementation (TDD-shaped,
    │                                    # contract matches tdd-cycle)
    ├── tester.md                        # phase-gate verification
    └── pr-review.md                     # local copy of pr-review aggregation
```

**Contracts**:

- `architect.Requires`: a phased plan (HLD shape).
- `architect.Ensures`: each phase has a green-lit implementation
  contract (in/out, test seeds).
- `implementer.Requires`: a single phase's implementation contract.
- `implementer.Ensures`: phase tests pass; commit recorded; no
  regressions.
- `tester.Requires`: a completed phase.
- `tester.Ensures`: a `pr-review` aggregated report for the phase +
  signoff or block.

**Composition**: keeps `implementer` contract-compatible with
`tdd-cycle` and `tester`'s gate contract-compatible with
`pr-review/coordinator`. v0.1 ships both as local files; cross-plugin
invocation is the future-evolution target.

**Source skills**: `skills/hld-phase-executor/`.

#### Phase 2 acceptance

1. `plugins/pr-review/`, `plugins/tdd-cycle/`,
   `plugins/feature-execution/` exist with the layout above.
2. Each plugin's `apm.yml` declares `openprose/prose` as a dep. No
   cross-plugin APM deps in v0.1.
3. Root `apm.yml` `marketplace.plugins` includes all three new
   entries.
4. `apm pack` regenerates `.claude-plugin/marketplace.json` to include
   all 7 plugins (4 existing + 3 new).
5. `apm marketplace check` passes.
6. Each prose program is invocable end-to-end from a consumer's repo
   via `apm install cajias/claude-skills/<program>` followed by
   `/<program>` in Claude Code.
7. Service contracts (`Requires` / `Ensures`) for `code-review` and
   the `pr-review` aggregation are byte-identical across the plugins
   that copy them, verified by a simple diff in CI.

## Open implementation questions (deferred to plan)

These are real questions but they are decisions for the implementation
plan, not blockers for the design:

- Exact wording of each service's `Requires` / `Ensures` block —
  drafted during extraction from source skills.
- Whether to ship a small `scripts/new-prose.sh` scaffold helper now
  or in Phase 2.
- Whether to vendor the `openprose/prose` skill at a pinned commit
  (defensive) or always pull head (current default).
- README rewrite scope: minimum is the install section; ideal is a
  fresh top-level doc that reflects the marketplace identity.

## Risks

- **`apm pack` round-trip fidelity**: if the regenerated
  `marketplace.json` differs in non-trivial ways from the
  hand-authored file, downstream consumers (anyone who already added
  the marketplace) might see plugin re-resolution. Mitigation: verify
  the diff in the migration commit; if cosmetic-only (key ordering,
  optional field omissions), document and accept; if structural, file
  an APM bug before merging.
- **Service contract drift**: as composite programs evolve, services
  accreted by reuse can develop conflicting expectations. Mitigation:
  each service's contract is the source of truth; composites must
  adapt to it, not vice versa. Service breaking changes get a major
  version bump.
- **OpenProse runtime dependency**: prose programs only function when
  `open-prose` is also installed. Mitigation: per-plugin APM dep on
  `openprose/prose`. If a consumer manually removes it, the slash
  command will fail loudly (skill not found) rather than silently.
- **Subagent-availability assumption**: multi-service programs assume
  Claude Code has subagents. On clients without that primitive,
  programs degrade to sequential execution. Mitigation: documented in
  the slash-command preamble; not a packaging concern.
