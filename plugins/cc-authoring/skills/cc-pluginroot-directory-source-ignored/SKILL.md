# Claude Code directory-source marketplace: pluginRoot ignored

## Problem

Claude Code refuses to load plugins from a local directory-source
marketplace and prints, for each affected plugin:

```
Plugin directory not found at path: <marketplace_root>/<plugin_name>.
Check that the marketplace entry has the correct path.
```

The directory IS present on disk — just at
`<marketplace_root>/plugins/<plugin_name>`, not at the resolved path
Claude Code is reporting. The marketplace.json's
`metadata.pluginRoot: "./plugins"` is being silently ignored.

The error message blames "the marketplace entry" but the entry is
correct per the documented schema; the bug is in the resolver.

## Context / Trigger Conditions

ALL of these together strongly point at this failure mode:

1. The marketplace was registered as `source: "directory"` (you can
   see this in `~/.claude/plugins/known_marketplaces.json` — look for
   `"source": "directory"` under the marketplace name).
2. Its `marketplace.json` includes `"metadata": { ..., "pluginRoot":
   "./plugins" }`.
3. Plugin entries use the factored short form, e.g.
   `{"name": "claudeception", "source": "./claudeception"}` —
   relying on `pluginRoot` to add `./plugins/` to that path.
4. Plugin subdirectories physically exist at
   `<root>/plugins/<name>`, NOT at `<root>/<name>`.
5. The error message shows the resolved path WITHOUT the
   `./plugins/` segment.
6. Only some plugins from the marketplace are reported — usually
   the ones currently enabled in settings or with cached install
   records — but ALL plugins in the marketplace are broken at
   runtime. The errors will spread to other plugins as soon as
   they're consulted.

## Root Cause

The Claude Code 2.1.158 binary's marketplace schema accepts
`metadata.pluginRoot` (validated as
`h.object({pluginRoot: h.string().optional()...})`). The field IS
read at multiple call sites (`H.pluginRoot`, `v.pluginRoot`,
`z.pluginRoot` are visible in the binary), but NONE of those call
sites are the source-resolution path for `source: "directory"`
marketplaces. For directory sources, the plugin source string is
joined directly against the marketplace's `installLocation` with no
`pluginRoot` prepending.

Result: a marketplace.json that validates fine at install time and
even passes APM's packaging step in `--dry-run` mode (since APM uses the same schema)
fails at plugin-load time.

Whether this is intentional ("pluginRoot is git-subdir only") or a
forgotten branch is unclear from the binary alone; the public docs
don't say. Either way the symptom is consistent.

## Solution

Revert the affected marketplace to **explicit per-plugin source
paths** and **remove `pluginRoot`** from `metadata`.

### Plain-hand-authored marketplace.json

```json
// before — broken
{
  "metadata": {
    "homepage": "...",
    "pluginRoot": "./plugins"
  },
  "plugins": [
    { "name": "foo", "source": "./foo" },
    { "name": "bar", "source": "./bar" }
  ]
}

// after — works
{
  "metadata": {
    "homepage": "..."
  },
  "plugins": [
    { "name": "foo", "source": "./plugins/foo" },
    { "name": "bar", "source": "./plugins/bar" }
  ]
}
```

### APM-managed marketplace

`apm.yml` is the source of truth and APM's packaging step regenerates
`marketplace.json`. You must fix BOTH:

1. Edit `apm.yml`:

   ```yaml
   marketplace:
     metadata:
       homepage: ...
       # remove this line:
       # pluginRoot: ./plugins
     packages:
       - name: foo
         source: ./plugins/foo   # make sure these are full paths
         ...
   ```

2. Re-run APM's packaging step. The generated `marketplace.json` will lose
   `pluginRoot` and contain explicit `./plugins/<name>` sources.

DO NOT edit only `marketplace.json` — the next run of APM's packaging step (or
the CI staleness check that repacks and runs `git diff --quiet`) will clobber
your hand-edit.

### One-line bulk rewrite for marketplace.json (Edit tool)

If many plugins, this `replace_all` Edit works because the literal
appears nowhere else:

- `"source": "./` → `"source": "./plugins/`

Then remove the `pluginRoot` line + clean up its preceding comma in
the `metadata` block.

After fixing, restart Claude Code. The errors disappear.

## Verification

1. JSON still parses:

   ```bash
   python3 -c 'import json; d=json.load(open(".claude-plugin/marketplace.json")); print(len(d["plugins"]), "plugins")'
   ```

2. No more `pluginRoot`:

   ```bash
   grep pluginRoot .claude-plugin/marketplace.json apm.yml || echo OK
   ```

3. All sources have the prefix:

   ```bash
   python3 -c '
   import json
   d = json.load(open(".claude-plugin/marketplace.json"))
   bad = [p["name"] for p in d["plugins"] if not p["source"].startswith("./plugins/")]
   print("missing prefix:", bad)
   '
   ```

4. Restart Claude Code. The `Plugin directory not found at path:` errors
   for every plugin in the marketplace stop firing.

## Example

Observed 2026-05-30 on Claude Code 2.1.158 (macOS arm64) with the
local marketplace at `/Users/<user>/Projects/workspace/claude-skills`.

PR #30 in that repo ("portable plugin paths") had switched from
explicit `./plugins/<name>` source paths plus no `pluginRoot` →
short `./<name>` sources plus `metadata.pluginRoot: "./plugins"`.
Schema-wise that's identical; APM happily packed it; but at runtime
Claude Code logged for two plugins:

```
Plugin directory not found at path:
  /Users/.../claude-skills/claudeception
  /Users/.../claude-skills/semantic-search
. Check that the marketplace entry has the correct path.
```

The fix reverted both `apm.yml` (removed `pluginRoot`, kept
`./plugins/<name>` in packages — they were already full there) and
regenerated `marketplace.json` via APM's packaging step. Diff was ~15 lines.

## Notes

- Don't trust that "the schema accepts it" means "the runtime
  applies it." For Claude Code 2.1.158 specifically, `metadata`
  fields can be silently ignored on some code paths.
- The error message — "Check that the marketplace entry has the
  correct path" — is misleading: the entry is correct per the
  documented schema. The bug is in the resolver, not the entry.
- This skill is paired with two closely related sibling skills:
  - `cc-plugin-cache-multi-version-not-recorded` — handles the
    different `not cached at (not recorded)` failure mode where
    cache parents have >1 version subdir.
  - `apm-marketplace-authoring-gotchas` — handles APM build-time
    issues (staleness check, prettier conflicts, etc.). Cross-link
    from there if updating.
- If a future Claude Code release fixes `pluginRoot` for directory
  sources, this skill becomes obsolete — check release notes before
  assuming the fix is still needed.
- Only some plugins appear in the error list because the resolver
  is lazy: it complains about plugins it tries to resolve (those
  enabled in settings, or with cached install records). All
  plugins in the marketplace are equally broken at runtime; you'll
  see the others surface the moment Claude Code tries to load them.
